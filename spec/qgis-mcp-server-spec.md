# QGIS MCP Server — Specification
Status: Draft v0.2
Author: Chloe (spec), Claude (drafting assistance)
Modelled on: existing Blender MCP tool surface (`Blender:execute_blender_code`, `get_objects_summary`, `get_screenshot_of_*`, `search_api_docs`, etc.)
---
## 1. Purpose
Provide an MCP server that exposes a running (or headless) QGIS instance to an LLM agent, so that map/layer/analysis work can be driven conversationally and iteratively — the same workflow the Blender MCP already provides for 3D scenes.
Primary use cases (Chloe-specific, informing priority order):
1. **Map commissions with a real-world GIS component.** Client work sometimes needs actual geographic data underneath the illustration (terrain, coastlines, hydrology, place data), not just freehand cartography.
2. **Real-world locations repurposed for fiction.** A recurring commission pattern: take a real city, street layout, or hill range and reuse it — sometimes lightly altered, sometimes wholesale — as the basis for a fictional or alternate-reality setting. Includes scenario work like the *Silver Elite* continent map (a sea-level-raised reimagining of the US), which was done manually last time and would benefit substantially from real elevation/hydrology data and GIS-driven sea-level modelling instead.
3. **Personal GIS art projects**, specifically the "3D terrain rendered over/with old maps" aesthetic — real elevation and hydrology data pulled from QGIS, then exported into Blender for the actual rendering. This makes **QGIS → Blender interoperability a first-class requirement**, not an afterthought: DEM/heightmap export, georeferenced textures, and vector-to-mesh-friendly formats all matter here.
4. Property due-diligence GIS work (flood risk, heritage overlays, constraint layers) — the original driver for learning QGIS, still relevant but secondary to the above now.
5. General PyQGIS learning — being able to ask for something and see it happen in the live app is the whole point.
---
## 2. Two operating modes (mirrors Blender MCP's live vs `_for_cli` split)
| Mode | Mechanism | Use case |
|---|---|---|
| **Interactive** | Companion QGIS plugin runs a small TCP listener inside a live QGIS session; MCP server forwards calls to it | Chloe has QGIS open, wants to see changes happen live, iterate visually |
| **Headless/CLI** | MCP server launches `qgis_process` or a standalone PyQGIS script (`QgsApplication` with no GUI) against a `.qgz`/`.qgs` project file | Batch jobs, scripted analysis, CI-style repeatable runs, no GUI needed |
This split is directly analogous to `execute_blender_code` (live addon) vs `execute_blender_code_for_cli` (background Blender process).

## 3. Architecture
```
┌─────────────┐      MCP (stdio/SSE)      ┌──────────────────┐
│ Claude/agent │ ───────────────────────▶ │  qgis-mcp-server  │
└─────────────┘                            │  (Python process) │
                                            └─────────┬────────┘
                                                       │
                          ┌────────────────────────────┴───────────────────────┐
                          │                                                    │
                 (interactive mode)                                  (headless mode)
                          │                                                    │
                   TCP socket                                      subprocess launch
                          │                                                    │
              ┌───────────▼────────────┐                          ┌───────────▼────────────┐
              │  QGIS Plugin (listener) │                          │  qgis_process / PyQGIS  │
              │  running inside live    │                          │  standalone script      │
              │  QGIS application       │                          │  (no GUI, one-shot)      │
              └──────────────────────────┘                          └──────────────────────────┘
```
- **Server language:** Python (matches PyQGIS binding language directly — no cross-language marshalling needed)
- **Transport to Claude:** standard MCP (stdio for desktop, SSE/HTTP for remote)
- **Transport to live QGIS:** local TCP socket opened by a lightweight QGIS plugin (`Plugins → Python Console` equivalent, but a persistent background listener rather than an interactive REPL). This is the same pattern the Blender MCP addon uses inside Blender.
- **Headless execution:** `qgis_process` (QGIS's built-in CLI for running Processing algorithms) plus direct `QgsApplication` initialization for anything `qgis_process` doesn't cover.
### 3.1 Provider adapter layer (backs §4.6)
The v1 provider list in §4.6 is not one API repeated five times — the providers share almost no interface, and an earlier draft's "new providers are added as a config entry (base URL, auth type, query pattern)" claim only holds for two of the five. Concretely:
| Provider | Protocol shape | Why config alone doesn't cover it |
|---|---|---|
| OS Data Hub | REST + API key | Genuinely RESTful; needs a collection/product mapping in code, but close to config-driven |
| OpenTopography | REST + API key | Closest of all to config-driven — a single parameterised GET returns the GeoTIFF |
| Natural Earth | **No query API at all** | A fixed catalogue of zipped downloads by scale (10m/50m/110m) and theme. "Search" is filtering a static manifest; there is no server-side bbox filtering, so the file is fetched whole and clipped locally |
| OpenStreetMap / Overpass | **Query language, not parameters** | Requires generating Overpass QL per data type and converting Overpass JSON into features. Type→QL templates are code, and large areas need splitting or they time out |
| BGS | **OGC WMS/WFS** | `GetCapabilities` to discover, `GetFeature` to fetch — a standard, but a wholly different protocol (OWSLib territory), layered on top of the free-625k/paid-tier distinction in §4.6 |
So `search_data_sources` dispatches to a **provider adapter** per source, behind one interface: declare capabilities (which data types, over what coverage extent, and whether credentials are required), `search(aoi, types) -> [Dataset]`, and `fetch(dataset, aoi, dest) -> path`. Rather than five unrelated implementations, adapters inherit from a small set of protocol-family bases — `RestApiAdapter` (OS, OpenTopography), `StaticCatalogueAdapter` (Natural Earth), `OverpassAdapter` (OSM), `OgcAdapter` (BGS) — so that the protocol is written once and a new provider within an existing family really is close to a config entry. It is only the claim that *every* new provider is config-only that was wrong.
Two dispatcher behaviours follow from this and are worth fixing here rather than leaving to implementation:
- **Coverage pre-filtering.** Each adapter declares its coverage extent, and the dispatcher skips non-covering adapters before making any network call — no querying OS Data Hub for a bounding box in Ontario. This also lets the agent answer "who could serve geology here" with no network traffic at all.
- **Bounded parallel fan-out with per-adapter timeouts.** Adapter queries are independent and should run concurrently, but Overpass and Nominatim both rate-limit, so concurrency is bounded and per-provider. One slow or broken provider must not stall or sink the whole menu — see REQ-10.
### 3.2 CRS policy
Providers disagree: OS and ONS serve EPSG:27700, OSM/Overpass and Copernicus serve EPSG:4326, Nominatim returns 4326, BGS varies by service. Any multi-provider acquisition per §4.6 therefore arrives mixed.
**Why this needs a policy rather than QGIS's on-the-fly reprojection.** Mixed CRS is genuinely fine for *display* — the canvas reprojects live and a mixed project looks correct. It bites in exactly three places: distance/area analysis, combining rasters, and export to Blender. The first two are recoverable. The third is not, and it fails silently: at Sudbury's latitude one degree of longitude spans ~68.5 km against ~111.2 km for latitude, so a 4326 DEM treated as a square grid renders terrain stretched east–west by roughly 62%. The output looks like entirely plausible terrain. It is simply not the shape of that place. The policy exists primarily to serve §4.7; everything else benefits incidentally.
**Target CRS is derived per area of interest, not fixed per install.** A fixed project CRS is fine for Suffolk and wrong the moment the *Silver Elite* continental work starts — no single projection suits both a market town and the contiguous US. The server derives a target per acquisition run and reports which it chose and why:
| Tier | Condition | Target |
|---|---|---|
| 1 | AOI within the UK | EPSG:27700 (British National Grid) |
| 2 | AOI fits within a single UTM zone (roughly <6° of longitude) | That UTM zone (EPSG:326xx / 327xx) |
| 3 | AOI spans multiple zones (continental) | **No automatic choice — the server asks.** See REQ-12 |
Layered on top of the tiers, one refinement that matters more than the tiers themselves: **prefer whichever candidate projected CRS leaves the highest-resolution raster in the set unresampled.** Something always gets resampled; it should be the 30 m global DEM, not the 5 m national one. For UK work this falls out for free — OS Terrain 5 is already 27700, so tier 1 costs zero resampling on precisely the layer the render is built from, and the coarser OSM/Copernicus layers reproject into it instead.
**Reprojection is eager, on registration, and the original is kept.** Lazy reprojection at operation boundaries would make every tool CRS-aware and invites the failure where two layers silently disagree. Eager costs one resampling pass and buys a homogeneous project. The downloaded original stays untouched on disk, so the resampling is always re-derivable if the target turns out to be wrong.
**AOI geometry travels as 4326; clip and export extents are defined in the target CRS.** Bounding boxes go to providers in 4326 because it is the one thing they all accept. But a 4326 bbox reprojected is not a rectangle — it is a slightly curved quadrilateral — so clipping to it yields a ragged edge and nodata to handle in Blender. Export extents are therefore specified in the target CRS, where the rectangle is a true rectangle.
**Vertical datums are recorded, not transformed** (REQ-13). This is the sleeper problem: horizontal CRS gets all the attention, but DEMs disagree vertically too. OS Terrain is ODN (Newlyn), Copernicus GLO-30 is EGM2008, SRTM is EGM96. ODN against EGM2008 in the UK is sub-metre to a couple of metres — ordinarily noise, except that `model_sea_level_change` works in single-metre increments, where a 2 m datum offset is a large fraction of the signal. Ellipsoidal heights sneaking in would be wrong by roughly 50 m in the UK, which floods everything or nothing. Full vertical datum transformation is a rabbit hole and is out of scope for v1; recording the datum and warning on conflict is cheap and converts a silent wrongness into a visible caveat.
> **An emergent contract worth naming.** REQ-6 (docs), REQ-7 (algorithm IDs), REQ-9 (place names) and now REQ-12 (tier 3) all resolve the same way: when the server cannot determine the right answer, it returns the candidates rather than guessing, and never fails bare. New tools should follow this shape by default — an extra round-trip is consistently cheaper than a confidently wrong result the agent cannot detect.

## 4. Tool surface (draft)
Naming follows the existing Blender MCP convention: `execute_*`, `get_*_summary`, `get_screenshot_*`, `search_*_docs`, `jump_to_*`.
### 4.1 Execution
- **`execute_pyqgis_code`** — run arbitrary PyQGIS code in the live session. Assign to `result` (dict, JSON-serialisable) to return data. Direct analogue of `Blender:execute_blender_code`.
- **`execute_pyqgis_code_for_cli`** — run PyQGIS code headless against a specified `.qgz`/`.qgs` project. Analogue of `execute_blender_code_for_cli`.
- **`run_processing_algorithm`** — invoke a named Processing algorithm (e.g. `native:buffer`, `qgis:zonalstatistics`) with a parameter dict; wraps `qgis_process` for headless or `processing.run()` for live. Worth a dedicated tool rather than forcing raw code, since Processing algorithms are QGIS's primary "batteries included" analysis surface and parameter dicts are easy for an agent to construct from docs.
### 4.2 Project / layer introspection
- **`get_project_summary`** — layer count by type (vector/raster/mesh), CRS, extent, active layer, layout count. Analogue of `get_blendfile_summary_datablocks`.
- **`get_layer_summary`** — for a named layer: geometry type, CRS, feature count, field schema, renderer type, source path, extent. Analogue of `get_object_detail_summary`.
- **`get_layers_tree`** — full layer panel structure incl. groups/nesting. Analogue of `get_objects_summary`.
- **`get_missing_layers`** — broken data source references (moved/renamed files). Analogue of `get_blendfile_summary_missing_files`.
- **`get_project_path_info`** — project file path, save state, CRS, last-modified. Analogue of `get_blendfile_summary_path_info`.
### 4.3 Visual feedback
- **`get_screenshot_of_canvas`** — render the current map canvas view to PNG. Analogue of `get_screenshot_of_area_as_image`.
- **`get_screenshot_of_window`** — full QGIS window screenshot (for layout/print composer work, dialog states). Analogue of `get_screenshot_of_window_as_image`.
- **`render_map_to_path`** — export current canvas or a named Print Layout to PNG/PDF at a given path/DPI. Analogue of `render_viewport_to_path`. **Mode-agnostic despite sitting in this section:** rendering a Print Layout is a standard headless operation, so this one falls under REQ-1b rather than REQ-1a. Only the *canvas* variant needs a live session, since a canvas view exists only in the GUI.
### 4.4 Navigation / view control
- **`zoom_to_layer`** — fit canvas to a named layer's extent. Analogue of `jump_to_view3d_object_by_name`.
- **`set_active_layer`** — set which layer is selected in the Layers panel.
- **`toggle_layer_visibility`** — show/hide a named layer or group.
### 4.5 Documentation lookup
- **`search_pyqgis_docs`** — full-text search over the bundled/cached PyQGIS API reference (mirrors `Blender:search_api_docs`). Given PyQGIS's docs are Sphinx-built and match the C++ class structure closely, this can likely reuse the same doc-indexing approach as the Blender skill almost verbatim.
- **`get_pyqgis_class_docs`** — direct lookup by identifier (e.g. `qgis.core.QgsVectorLayer`), same discovery-pattern (`X.*`) behaviour as `Blender:get_python_api_docs`.
- **`search_processing_algorithms`** — list/search available Processing algorithm IDs and their parameter schemas (`native:buffer`, `gdal:*`, `grass:*`, `saga:*`). No Blender equivalent needed — this is QGIS-specific and important since algorithm parameter names aren't always guessable.
### 4.6 Data acquisition & source discovery
This is arguably as important as any analysis tool — a large share of real GIS friction is finding, licensing, and downloading the right dataset before any actual work can start. Targets known open sources rather than generic web search, since GIS data portals have their own query patterns (bounding box, place name, dataset ID) that generic search handles poorly.
- **`resolve_place`** — resolve a place name to geographic extents before any data lookup happens. Returns *all* plausible candidates ranked, never a single silently-chosen best match, each with: display name, feature type (town/county/hill/etc.), administrative context, a bounding box, and — where the provider has one — the actual boundary polygon. This is a distinct tool rather than an internal step inside `search_data_sources` for a specific reason: the disambiguation behaviour described in §4.6.2 step 1 is only implementable if the *agent* can see that three Sudburys came back. If resolution were buried inside the search call, the server would have to pick one silently and the agent would never know a choice had been made.
  - **Bbox and polygon are both returned deliberately.** A bounding box is the right AOI for the terrain pipeline (heightmaps are rectangular), but the wrong one for clipping buildings and streets to a settlement — a bbox around Sudbury includes a good deal of surrounding farmland. §4.6.2 step 4 wants the built-up area boundary specifically, so `clip_to_aoi` (§4.7) accepts either form and the agent picks per layer.
  - **Provider tiering:** **ONS Open Geography Portal** (UK Built-Up Areas, parishes, wards, LADs — authoritative OGL polygons, no key) and **OS Names** (via the OS Data Hub key, high-quality UK place lookup) where the place resolves to the UK and credentials are present; **Nominatim** (OpenStreetMap) as the global fallback and the no-key default, since it needs no registration, covers everywhere, and returns both candidate lists and — with `polygon_geojson` — real boundary polygons rather than only rectangles.
  - **Nominatim usage policy** caps requests at 1/second and requires an identifying User-Agent. Comfortable for single-user desktop use, but resolutions SHALL be cached to a local store regardless: it keeps usage well inside policy, and it makes the §9 tests deterministic without needing to mock the geocoder at all.
- **`search_data_sources`** — query across a configured set of known providers by bounding box or AOI polygon (or by place name, resolved per REQ-9), AND one or more requested data types in a single call (e.g. `["elevation", "buildings", "streets", "geology"]`), returning matching datasets grouped by type, each with resolution/scale, format, licence, provider, and approximate size. Deliberately multi-type rather than one-provider-per-call, so a compound request ("get me terrain, buildings, streets, and geology for this place") produces one grouped result set the agent can present as a single menu, instead of the agent having to guess which providers to query separately. Configured providers for v1:
  - **OS Data Hub** (Ordnance Survey) — UK topography, OS Terrain 50/5, building/street data. Relevant to UK commission and property work.
  - **OpenTopography** — global DEM access (SRTM, Copernicus GLO-30, national LiDAR where available). Primary elevation source for the terrain/Blender pipeline (§4.7).
  - **Natural Earth** — coastlines, admin boundaries, rivers at multiple scales. Good generic base layer, especially as a starting skeleton for fictional/alternate-reality maps.
  - **OpenStreetMap (via Overpass API)** — street layouts, building footprints, place names, points of interest. Directly serves the "lift a real city's street grid for a fictional setting" use case, and covers buildings/streets where OS Data Hub coverage is unavailable or licence terms don't fit.
  - **BGS (British Geological Survey)** — geology data type added as a core provider given how frequently this comes up for Chloe's terrain/cartography work. BGS Geology 625k (national scale) is free under OGL and covers vector bedrock/superficial-deposit polygons — commission-safe, no licence fee. Higher-resolution tiers (250K/50K/25K/10K) exist but carry a per-area commercial licence fee, so `search_data_sources` results for geology should surface the 625k free tier by default and flag the higher-res paid tiers as a distinct option with their licence terms shown up front (see `get_dataset_licence_info`) rather than silently picking the highest resolution available. BGS's GeoIndex also supports direct clip-to-extent, which the download step can mirror to avoid pulling more than needed.
  - Extensible list — new providers are added as a **provider adapter** (§3.1), not as new tool code in `search_data_sources`. Within an existing protocol family a new provider is close to a config entry (base URL, auth type, query pattern); a provider introducing a new protocol shape needs a new family base class. See §3.1 for why the five v1 providers do not share one interface.
- **`download_and_register_layer`** — download a specific dataset (from a `search_data_sources` result or a direct URL) and add it to the project as a layer in one step. Requires confirmation before executing per REQ-4d (state source, format, licence tier and approximate size before proceeding) — this is the one tool in the whole spec that's genuinely fetching external, un-trusted-until-verified data, so it shouldn't be silently automatic. Designed to be called once per selected dataset in a loop by the agent (see §4.6.1) rather than needing a bespoke "download everything" variant.
- **`get_dataset_licence_info`** — surface the licence/attribution terms for a dataset before or after download (e.g. OS Data Hub's OGL vs commercial tiers, OSM's ODbL attribution requirement, Natural Earth's public domain status). Matters specifically because commission work (§2, use case 1) may have redistribution/attribution obligations that differ per source — this shouldn't be left implicit.
- **`check_api_credentials`** — report which configured providers have valid API keys set up locally and which are missing credentials, rather than failing opaquely mid-download. Some sources (OS Data Hub, OpenTopography) require free registration for an API key — the MCP can't complete that signup step itself (falls under the same "account creation" restriction as any other service), so this tool's job is to clearly surface what's missing and point at the registration page, not attempt to work around it.
#### 4.6.1 UX pattern: discovery menu → automated fetch
This is the intended end-to-end interaction shape, and it's deliberately achieved through orchestration of the primitives above rather than one monolithic "get me everything" tool — keeps each tool testable in isolation (§9) while still giving a one-request, one-menu, one-confirmation experience in practice:
1. **Chloe asks in natural language** for what she wants at a place and rough scale (e.g. "Sudbury height map with buildings and streets" — see worked example below). No need to specify provider names or dataset IDs.
2. **Agent resolves the location, then calls `search_data_sources`** once, with the implied data types inferred from the request (elevation + buildings + streets, in the example). Resolution goes through `resolve_place` — either as an explicit prior call, or implicitly by passing `place` to `search_data_sources` and letting REQ-9 handle it, which proceeds silently when the name is unambiguous and returns the candidate list when it isn't. Multiple providers may return options for the same type at different resolutions/licences.
3. **Agent presents the grouped results as a menu** — conversationally, not as a literal UI widget — e.g. "For elevation: OS Terrain 5 (5m, OGL) or Copernicus GLO-30 (30m, free); for buildings: OS building outlines or OSM building footprints; for streets: OSM road network." Chloe picks per-category or says "just use the best UK-native option for everything."
4. **Missing credentials surface on their own.** REQ-10 means the step-2 search already returned a per-provider status, so a provider lacking a key appears in the menu flagged as unavailable rather than failing later. `check_api_credentials` is therefore a diagnostic to reach for when Chloe asks what is set up, not a mandatory pre-flight on every run — an earlier draft had it as a required step here, which REQ-10 has since made redundant.
5. **Agent calls `download_and_register_layer`** once per selected dataset (looping over the picks), each with its own confirmation per REQ-4d — but since these happen in one continuous turn immediately after Chloe's selection, it reads as a single automated step from her side, not a manual multi-step process.
6. **Agent chains into `clip_to_aoi`** to trim everything to the actual area of interest, since provider extents are typically larger than the requested area.
7. From there the terrain/export tools (§4.7) or ordinary analysis tools (§4.1–4.5) pick up as normal — acquisition is a front-end to the rest of the tool surface, not a separate workflow.
No new tool is required for this pattern beyond what's already in §4.6 — it's a question of the agent's calling discipline, which should be documented as guidance in the eventual system prompt / plugin instructions for whatever surfaces this MCP, not enforced mechanically by the server.
#### 4.6.2 Worked example: Sudbury heightmap with buildings and streets
Illustrates the pattern above end-to-end, and doubles as a natural first integration test once `download_and_register_layer` has live coverage (§9.3's data-acquisition row).
> **Chloe:** "Sudbury height map with superimposed buildings and streets."
1. Agent calls `resolve_place("Sudbury")`, which returns several candidates (Sudbury, Suffolk; Sudbury, Ontario; Sudbury, London) — genuinely ambiguous, so per REQ-9 nothing is chosen for it. The agent asks one clarifying question, or proposes the most contextually likely match (Suffolk, given Chloe's known location and prior property research there) and states the assumption. Note this is the case REQ-9 exists for: had it guessed, the run would have quietly produced a Canadian mining town's terrain.
2. `search_data_sources(bbox=<Sudbury, Suffolk extent from step 1>, types=["elevation", "buildings", "streets"])` → menu: OS Terrain 5 / Copernicus GLO-30 for elevation; OS building outlines / OSM buildings for buildings; OSM road network for streets.
3. Chloe picks OS Terrain 5 (best UK resolution) + OS buildings + OSM streets, or simply says "best available."
4. Agent runs `download_and_register_layer` three times (one per dataset), each confirmed inline, then `clip_to_aoi` — using the bounding box for the DEM (rectangular, no ragged nodata edge to handle in Blender) and the ONS Built-Up Area polygon from step 1 for the buildings and streets (so the render isn't fringed with isolated farm tracks running off into the countryside).
5. Result: three correctly-clipped, correctly-projected layers in the open project — DEM, building footprints, road network — ready either for further QGIS styling or, per Chloe's actual goal, straight into the §4.7 export tools (`export_heightmap` for the terrain, `export_vector_layer_for_mesh` for buildings/streets) for the Blender rendering pipeline.
### 4.7 Terrain, elevation & Blender export
Added specifically for the terrain/old-map rendering pipeline and real-location reuse work (use cases 2 and 3 above). These lean heavily on existing QGIS raster/DEM tooling and Processing algorithms rather than needing custom code.
- **`fetch_elevation_data`** — pull DEM/elevation data for a given extent, built on top of `search_data_sources`/`download_and_register_layer` (§4.6) for the actual source lookup and fetch, then clips to the specified extent. Being a fetch, it carries REQ-4d confirmation exactly as the underlying `download_and_register_layer` does — a convenience wrapper must not become a way to skip the gate. Kept as a separate convenience tool rather than requiring the agent to chain the generic acquisition tools manually every time, since "get me elevation for this area" is by far the most common data-acquisition need across all three use cases in §2.
- **`model_sea_level_change`** (renamed from `apply_sea_level_offset`) — model a raised or lowered sea level against a DEM. Directly targets *Silver Elite*-style scenario work — turns a manual multi-step Photoshop-era process into one parametrised call.
  - **The DEM is not modified.** Sea level rise of N metres is computed by thresholding — land is where elevation > N — not by subtracting N from every elevation value. The arithmetic is nearly the same; the consequences are not. Offsetting the raster in place leaves every downstream product wrong by N: the heightmap exports at the wrong absolute range, the hillshade is computed from falsified elevations, and any later `model_sea_level_change` call compounds the error. The tool therefore reads the DEM and emits new derived layers beside it.
  - **Outputs:** a binary land/water mask raster; a polygonised water/coastline vector layer (the new shoreline, which is the actual deliverable for cartography); and optionally a depth-below-new-sea-level raster (`N - elevation`, clamped at zero) which is what you want if the render needs shallow water shading differently from deep. An offset DEM can be produced too, but only as an explicitly requested, explicitly named secondary output — never as the primary result.
  - **`connectivity` option — matters more than it sounds.** Naive thresholding (the "bathtub model", the default) floods *every* cell below the threshold, including inland basins with no path to the sea. Real sea level rise cannot reach a landlocked depression, so physically-correct modelling needs a flood fill seeded from the ocean edge (`connectivity="ocean"`). For fiction the bathtub model is often the *desirable* one — it hands you inland seas across the American interior, which is exactly the kind of thing the *Silver Elite* map wants — but that should be a chosen option, not an artefact of the simplest implementation. Both are supported; the default is documented rather than accidental.
- **`export_heightmap`** — export a DEM (or a derived layer) as a grayscale heightmap for a Blender displacement/geometry-nodes workflow. Three things about this are load-bearing enough to be requirements rather than implementation details (REQ-11), because each fails *silently* — producing a plausible-looking image that renders wrong:
  - **16-bit minimum, never 8-bit.** 8-bit gives 256 elevation steps; across a 300 m range that is 1.2 m per step, which reads as visible stair-stepping on any rendered hillside. 16-bit gives ~4.6 mm steps over the same range. Default output is 16-bit PNG (portable, Blender reads it directly); float OpenEXR is offered for maximum fidelity, and GeoTIFF for round-tripping back into GIS.
  - **Nodata must be excluded before normalising.** DEM nodata is typically -9999 or -32768. Left in, it becomes the normalisation minimum, and the entire real terrain gets crushed into the top fraction of a percent of the output range — a heightmap that looks like a flat plate with one hole in it. Nodata is excluded from the min/max computation and mapped to an explicit fill value.
  - **The scaling metadata is part of the output.** See REQ-11 — an image alone cannot tell Blender how tall the terrain is.
  - *Blender-side gotcha worth carrying into the install docs:* the heightmap image must be set to **Non-Color** in Blender. Left as sRGB, the colour transform is applied to the height values and the terrain comes out the wrong shape — subtly enough to be mistaken for bad source data.
- **`export_georeferenced_texture`** — export the current canvas render (or a specific layer combination — e.g. old-map raster overlay + hillshade + BGS geology polygons styled by rock type) as a texture image, plus its world-space bounding box, so it can be UV-aligned against a heightmap-derived mesh in Blender. Geology data (§4.6) is a natural texture source here — bedrock/superficial-deposit boundaries add real geological character under a rendered terrain without needing to hand-paint it.
- **`export_vector_layer_for_mesh`** — export vector layers (roads, coastline, contours) to a mesh-friendly format (e.g. GeoJSON with elevation-sampled Z values, or OBJ/SVG) for use as Blender curve/mesh input — useful for turning real street layouts or hill contour lines into fictional-map basework.
- **`clip_to_aoi`** — clip any layer (vector or raster) to a named area of interest (bounding box, drawn polygon, another layer's extent, or a boundary polygon returned by `resolve_place` per §4.6) — the standard first step when lifting a real city/region as a base for fictional reuse. Accepting both a bbox and a polygon is deliberate rather than redundant: the same acquisition run typically wants a rectangular clip for the DEM (heightmaps are rectangular, and a ragged edge means nodata to deal with in Blender) and a boundary-polygon clip for buildings and streets (so the render isn't fringed with isolated farm tracks). The agent chooses per layer, not per run.
This is the set that most directly serves the "beautiful 3D terrain + old map" aesthetic and the take-a-real-place-and-fictionalise-it workflow — it's arguably a bigger differentiator for Chloe's actual use than the general-purpose analysis tools in 4.1–4.5, and should be weighted accordingly in build order (see §7).
### 4.8 Explicitly out of scope for v1
- Editing/writing features into a layer's attribute table (data-mutating — treat like the existing "explicit permission required" action category; revisit once read-heavy tools are proven out). Note that this exclusion is about *dedicated tools*: it does not mean feature editing is impossible in v1, since `execute_pyqgis_code` can do it directly and no static check can prevent that (see REQ-4a–4c). The distinction being drawn is that mutation should require deliberately dropping to raw code, not be available as a one-call convenience tool, and that raw-code mutation carries a project backup rather than a confirmation prompt.
- Vertical datum transformation between geoid models (ODN / EGM2008 / EGM96). Datums are recorded and conflicts warned about per REQ-13, but not converted — see §3.2 for why recording is enough for v1 and conversion is not.
- Publishing to QGIS Server / hosted services
- Plugin installation/management

## 5. Requirements (EARS notation)
**REQ-1 (connection):** WHEN a live QGIS session with the listener plugin active is available, the qgis-mcp-server SHALL connect to it over a local TCP socket.
**REQ-1a (no silent fallback):** IF a tool that names its execution mode is called AND the mode it names is unavailable, THEN the server SHALL return an explicit error naming the missing mode rather than executing in the other one. This covers `execute_pyqgis_code` and `execute_pyqgis_code_for_cli` (§4.1), the two screenshot tools in §4.3, and all of §4.4 (navigation/view control). Note `render_map_to_path` is deliberately *not* in this list: Print Layout rendering works headless, so it is mode-agnostic per REQ-1b, and only its canvas variant requires a live session. Rationale: a live-mode call that silently ran headless would execute against a project file with no visible effect on Chloe's screen, which is indistinguishable from the tool having failed — the worst possible failure mode for the interactive loop the whole of §2 exists to serve.
**REQ-1b (mode selection for mode-agnostic tools):** WHERE a tool does not name its execution mode (`get_project_summary` and the rest of §4.2, `run_processing_algorithm`, and the §4.6/§4.7 sets), the server SHALL prefer the live session when one is reachable, fall back to headless against the configured project file when it is not, AND report which mode served the call in the tool's response. The reported mode is not cosmetic: for `download_and_register_layer` and `run_processing_algorithm` (which per §8 auto-adds outputs to the project) it is the only way to know whether the resulting layer landed in the open canvas or in a project file on disk.
**REQ-2 (headless fallback):** WHEN no live session is available AND a project file path is supplied, the qgis-mcp-server SHALL execute requests via `qgis_process`/standalone `QgsApplication` without requiring the QGIS GUI to be open.
**REQ-3 (data return):** WHEN `execute_pyqgis_code` or `execute_pyqgis_code_for_cli` is called, the server SHALL return only JSON-serialisable data assigned to a `result` variable, mirroring the Blender MCP contract, to keep the calling convention consistent for the agent.
**REQ-4 (destructive actions):** IF a request would delete a layer, overwrite a project file, or modify features, THEN the server SHALL require an explicit `confirm=true` parameter, since QGIS has no native undo across a scripted session the way manual GUI edits do.
**REQ-4a (raw execution is exempt, but backed up):** WHERE a tool executes agent-authored code (`execute_pyqgis_code`, `execute_pyqgis_code_for_cli`), confirm-gating per REQ-4 SHALL NOT apply, since the server cannot statically determine whether submitted code is destructive, and gating every call would make the interactive loop (§2, and use case 5 in §1) unusable. INSTEAD, before executing, the server SHALL write the current project state to a timestamped backup and SHALL return that backup's path in the tool response.
**REQ-4b (backup mechanics):** WHEN taking a REQ-4a backup, the server SHALL serialise the *current in-memory* project (`QgsProject.instance().write(<backup_path>)`) rather than copying the project file from disk, since in live mode the on-disk file may be stale by an arbitrary amount of unsaved work. Backups SHALL be written to a configurable directory (defaulting to a central per-user cache location, not the project directory, so that unsaved/untitled projects are still covered), named by project name plus ISO timestamp, and SHALL be pruned to a configurable retention count (default: 20 most recent per project).
**REQ-4c (stated limits of the backup):** The REQ-4a backup covers project structure only — layer references, styling, layouts, project CRS and settings. It does NOT cover the underlying data: raw code that truncates a data provider, overwrites a GeoTIFF, or deletes a shapefile on disk is unprotected by it. The server SHALL state this limit in the tool description for both raw-execution tools rather than letting "a backup was taken" imply more coverage than it has. Restoring a backup in v1 is a manual step (open the backup `.qgz`); a `list_project_backups`/`restore_project_backup` pair is deferred to the same later phase as the other write operations (§7, task 8).
**REQ-4d (external data fetch):** IF a tool fetches data from an external provider (`download_and_register_layer`, and `fetch_elevation_data` which wraps it), THEN the server SHALL require explicit confirmation stating source, format, licence tier and approximate size before proceeding. This is a *separate* gate from REQ-4, not an instance of it: REQ-4 guards against irreversible local change, whereas this guards against pulling external, un-verified data of unknown size and unknown licence terms. Earlier drafts cited REQ-4 as the basis for the download prompt, but none of REQ-4's three triggers — deleting a layer, overwriting a project, modifying features — describes a download, so the rule had no requirement actually backing it. `fetch_elevation_data` is named explicitly because its convenience wrapping is exactly how a fetch could otherwise slip through unconfirmed.
**REQ-5 (screenshots):** WHEN `get_screenshot_of_canvas` is called, the server SHALL return a PNG capped at a configurable byte-size limit (default: MCP message size limit), matching the Blender MCP screenshot contract.
**REQ-6 (docs):** WHEN `search_pyqgis_docs` is called with an identifier that has no exact match, THEN the server SHALL return the nearest namespace/partial match with suggested siblings, rather than a bare "not found," matching the Blender `get_python_api_docs` fallback behaviour.
**REQ-7 (algorithm discovery):** WHEN `run_processing_algorithm` is called with an unrecognised algorithm ID, THEN the server SHALL return the list of algorithm IDs matching a fuzzy search on the given name, to reduce failed round-trips from slightly-wrong IDs (e.g. `native:buffer` vs `qgis:buffer`, which differ across QGIS versions).
**REQ-8 (grouped data discovery):** WHEN `search_data_sources` is called with more than one requested data type, THEN the server SHALL return results grouped by type across all matching providers in a single response, rather than requiring one call per type, so the agent can present a single combined menu per the §4.6.1 interaction pattern.
**REQ-9 (place resolution and ambiguity):** WHEN `search_data_sources` is called with a `place` string rather than a bounding box or AOI polygon, THEN the server SHALL resolve it via `resolve_place` and proceed automatically IF exactly one candidate is returned above the configured confidence threshold; OTHERWISE it SHALL return an error enumerating the candidates with their types and administrative context, rather than selecting one. This mirrors the fallback contract already established by REQ-6 and REQ-7 — never fail bare, always return the near-misses — so that ambiguity costs one extra round-trip rather than silently producing data for the wrong continent's Sudbury.
**REQ-10 (degraded provider results):** WHEN `search_data_sources` fans out to provider adapters (§3.1) AND one or more adapters fail, time out, or are skipped for missing credentials, THEN the server SHALL return the results from the adapters that succeeded, together with a per-provider status for those that did not, rather than failing the call. A single unreachable provider must never cost the whole menu — the §4.6.1 pattern depends on one call producing one combined menu, and a partial menu with "BGS: skipped, no API key" attached is far more useful than an error. This also means a missing key surfaces inline during search rather than only via a separate `check_api_credentials` pre-flight.
**REQ-11 (heightmap output contract):** WHEN `export_heightmap` is called, the server SHALL write at least 16 bits per channel, SHALL exclude nodata from the normalisation range, and SHALL return alongside the file the values needed to set displacement correctly in Blender: the source elevation min and max in metres that were mapped to the output's full range, the ground extent width and height in metres, and the derived ratio `(max_elev - min_elev) / extent_width` — the displacement strength for a plane one Blender unit wide, with the aspect taken from the returned extent width and height (AOIs are frequently not square, so a literal 1×1 plane would itself distort the terrain). Rationale: a heightmap image carries no absolute scale, so without this the vertical exaggeration is set by eye, which is both wrong and irreproducible between exports. This further means the ground extent must be expressed in metres, which requires the DEM to be in a projected CRS — an EPSG:4326 DEM yields an extent in degrees and a meaningless ratio. The server SHALL therefore reject or reproject a geographic-CRS DEM here rather than emitting a ratio computed from degrees, per the CRS policy in §3.2 and REQ-12.
**REQ-12 (target CRS selection):** WHEN layers are acquired per §4.6, the server SHALL reproject them on registration to a single projected (metre-based) target CRS derived from the area of interest per the §3.2 tiers, SHALL retain the unmodified downloaded original on disk, and SHALL report the chosen CRS and the tier that selected it. WHEN a §4.7 export runs, the server SHALL verify its input is already in a projected CRS rather than reprojecting at export time — by then the target is settled, and a silent reprojection during export would be a second resampling of the layer the render is built from. IF the AOI spans multiple UTM zones (tier 3), THEN the server SHALL NOT select a projection automatically, and SHALL instead return the candidate projections for the agent to put to Chloe — any standard EPSG code covering the AOI (e.g. EPSG:5070 NAD83 / Conus Albers for the contiguous US, EPSG:3035 for Europe) alongside an equal-area or conformal projection centred on the AOI, with the trade-off stated. Rationale: at continental scale the choice between equal-area and conformal is a cartographic decision with a visible effect on the finished map, not a technical default the server is entitled to make on Chloe's behalf; and continental AOIs are rare enough that one question costs little.
**REQ-13 (vertical datum is recorded, not transformed):** WHEN a DEM is acquired, the server SHALL record its vertical datum (e.g. ODN, EGM2008, EGM96, or unknown) as layer metadata. WHEN `model_sea_level_change` runs against a DEM whose vertical datum is unknown, OR WHEN two DEMs with differing vertical datums are combined, THEN the server SHALL emit a warning naming the datums involved and SHALL proceed rather than blocking. Vertical datum transformation itself is out of scope for v1 (§4.8). Rationale: sea level modelling operates in single-metre increments, so a datum mismatch of a metre or two is a large fraction of the modelled signal, and ellipsoidal heights would be wrong by roughly 50 m in the UK — but implementing geoid transformation is disproportionate to v1, and a visible caveat removes the silence, which is the actual danger.

## 6. Design notes / risks
- **PyQGIS environment setup is the main friction point historically** — `PYTHONPATH`/`QGIS_PREFIX_PATH` must point at the QGIS install's bundled Python bindings. The server's install docs need a clear per-OS setup script (this has tripped up most PyQGIS standalone-script tutorials found during research).
- **Version drift:** PyQGIS is "nearly identical" to the C++ API and both move with each QGIS release (currently 3.44 LTR / 4.2 latest as of this spec). Pin the doc-index and tested API surface to whichever version Chloe runs locally, and treat cross-version calls as a known limitation rather than silently failing.
- **Threading:** the live listener plugin has a harder constraint than "don't block the event loop". PyQGIS GUI objects — the map canvas, the layer tree, the project in a GUI session — are **main-thread-only**, and touching them from another thread does not raise a Python exception, it segfaults QGIS. So the danger is not a frozen GUI, it is losing unsaved work to a crash.
  - **The pattern:** the socket listener accepts and reads on a background thread, but never executes there. Submitted work is marshalled onto the main thread — `QTimer.singleShot(0, callable)`, or a signal connected with `Qt.QueuedConnection` to a slot owned by a main-thread object — and the background thread blocks on a future/event for the result before writing the response. This is structurally the same trick the Blender MCP addon uses, pulling queued work onto Blender's main thread via a modal timer operator.
  - **Accept the consequence honestly:** main-thread execution means a long operation *does* freeze the GUI for its duration. That is unavoidable for anything canvas-touching and should not be papered over. Mitigate with a timeout on the socket side so the agent receives an error rather than hanging indefinitely, and keep the timeout configurable, since a legitimate Processing run on a large raster can take minutes.
  - **`QgsTask` is still the right tool, but only for the compute half.** The earlier draft's "run submitted code in QGIS's task mechanisms" is wrong as a blanket rule — a `QgsTask` that touches the canvas will crash. The correct division is: heavy computation that touches no GUI state can and should run in a `QgsTask` off the main thread; applying its results to the project or canvas comes back to the main thread. For `run_processing_algorithm` specifically this is worth doing, since those are the calls long enough for the freeze to be felt.
- **Processing algorithm dict-building** is probably the highest-leverage tool for Chloe's actual use cases (buffers, zonal stats, flood/heritage overlay intersections) — worth prioritising `run_processing_algorithm` + `search_processing_algorithms` over raw `execute_pyqgis_code` in the build order, even though raw execution is the more "general" capability.
- **API key setup for data sources (§4.6)** is a one-off manual step, not something the MCP can automate — free registration with OS Data Hub and OpenTopography is required before those providers are usable, and account creation stays outside what the server should attempt on Chloe's behalf. The install docs need a short "register here, put the key in this config file" checklist alongside the PYTHONPATH setup steps already needed for PyQGIS itself.

## 7. Suggested build order (tasks.md outline)
0. **Create synthetic test fixtures** (`test-data/`) — tiny deterministic DEM, sample vector layer, one small real-world CRS test clip. See §9.2/9.6 — everything downstream depends on this existing first.
1. Headless `execute_pyqgis_code_for_cli` — no plugin needed, proves the PyQGIS environment/path setup works at all. Paired test: run trivial code against fixture, assert structured return.
2. `get_project_summary` / `get_layer_summary` headless — read-only introspection, low risk. Paired test: assert exact fixture properties (feature count, CRS, field schema).
3. `run_processing_algorithm` + `search_processing_algorithms` headless — highest practical value for real analysis tasks, and the foundation the terrain tools (§4.7) and data acquisition tools (§4.6) are built on top of. Paired test: known algorithm + fixture input → hand-calculable expected output.
4. **Data acquisition set (§4.6)** — `resolve_place` first, since `search_data_sources` depends on it for any place-name input and REQ-9's ambiguity contract is easiest to get right before anything is layered on top; then `search_data_sources`, `get_dataset_licence_info`, `check_api_credentials` (no external network calls needed for their tests — mock provider responses against fixtures, and for `resolve_place` use cached real Nominatim/ONS responses per §4.6, which removes the need to mock the geocoder at all); `download_and_register_layer` last, since it's the one tool that needs real network calls and confirm-gating (REQ-4d) properly wired up before it's safe to use unattended. The §3.2 CRS policy is implemented here, since registration is where reprojection happens — tiers 1 and 2 are deterministic and testable offline against the fixture; tier 3's ask (REQ-12) needs no projection maths at all, only the candidate list. **This task is per-adapter, not all-or-nothing** (§3.1): build the dispatcher plus one adapter — OpenTopography is the natural first, being the closest to config-driven and the one serving the highest-priority data type — then add providers one at a time behind the same interface. Each addition is independently shippable and independently testable, and REQ-10 means a half-populated provider list still returns a working menu. Note that the five v1 providers span four distinct protocol families, so this task is materially larger than the tool count suggests.
5. **Terrain/Blender export set (§4.7)** — `fetch_elevation_data`, `clip_to_aoi`, `export_heightmap`, `export_georeferenced_texture` first (these are largely thin wrappers over Processing algorithms + raster export, so low incremental cost once #3 and #4 exist); `model_sea_level_change` and `export_vector_layer_for_mesh` next. Pulled forward in priority given this is the use case with the clearest, most distinctive payoff (map commissions, fictional-location reuse, and the old-map/3D-terrain art projects all depend on it). Paired tests per §9.3 table — file existence/format/dimensions/stats assertions.
6. Live listener plugin (`execute_pyqgis_code`, screenshots, view control) — once headless path is solid, add the interactive loop. Covered by the lighter smoke-test pass (§9.4) rather than full unit coverage.
7. Documentation search tools — can be built in parallel any time; no dependency on the above.
8. Destructive/write operations — deferred until the above is stable and confirm-gating (REQ-4) is implemented.
Each numbered task above is expected to produce both the tool and its test in the same unit of work (REQ-T1) — this list is the skeleton for `tasks.md` in the SDD three-file structure, with `requirements.md` covering §5/§9.5 and `design.md` covering §3/§6.

## 9. Testing strategy
Goal: every tool in §4 should be verifiable by the agent itself during a Claude Code build session, without Chloe needing to open QGIS and eyeball results. This follows the same three-file SDD approach as the UBS work (requirements → design → tasks), with testability treated as a first-class requirement rather than an afterthought bolted on at the end.
### 9.1 Why this is tractable for QGIS specifically
Unlike Blender (where "does it look right" is often genuinely visual and needs a human), most QGIS operations produce **structured, assertable output**: feature counts, CRS strings, geometry validity, raster statistics (min/max/mean elevation), file existence and format. The agent can check "did this work" programmatically for the large majority of tools without needing to look at a picture. Screenshots remain useful as a supplementary check (Claude can read an image directly), but shouldn't be the primary pass/fail signal.
### 9.2 Test harness
- **Framework:** QGIS ships its own `qgis.testing` module (`start_app()`, `QgsApplication` bootstrapping) built on standard Python `unittest` — this is the same mechanism QGIS's own core test suite uses, so it's a well-trodden path rather than something bespoke.
- **Fixtures:** a small `test-data/` directory of synthetic, deterministic inputs — a tiny DEM (e.g. 50×50 px GeoTIFF with a known elevation pattern), a handful of vector features with known geometry/attributes, one small real-world clip (e.g. a known UK grid square) for CRS/reprojection tests. The DEM fixture SHALL deliberately include **nodata cells** and a **landlocked basin below sea level**, since those are the two cases that separate a correct terrain implementation from one that merely looks correct (REQ-11's normalisation trap and `model_sea_level_change`'s connectivity option respectively) — a clean synthetic DEM would let both bugs through. Synthetic and tiny by design, so tests run in seconds and results are exactly predictable (no "roughly looks right" ambiguity).
- **Isolation:** tests run against the headless path (`execute_pyqgis_code_for_cli` / `qgis_process`) by default, since it requires no GUI and is what CI-style automated runs need. Live-listener-plugin tools get a thinner smoke-test layer (§9.4) rather than full coverage, since spinning up a real GUI session in an automated run is inherently more fragile.
### 9.3 Per-tool test pattern
Each tool ships with a paired test that asserts on structured output, not visual inspection:
| Tool category | Assertion style |
|---|---|
| Introspection (`get_layer_summary`, etc.) | Exact match against known fixture properties (feature count, CRS EPSG code, field names/types) |
| CRS policy (§3.2) | Tier selection asserted against AOIs with known correct answers — a Suffolk bbox resolves to EPSG:27700, a single-zone non-UK bbox to its UTM zone, a continental bbox returns candidates rather than a CRS (REQ-12). Reprojection asserted by round-tripping the real-world fixture clip and checking the geometry lands within tolerance of its known true coordinates, plus that the original file on disk is byte-identical afterwards. The highest-resolution-raster refinement gets its own case: given a 27700 DEM and a 4326 vector, assert the DEM was not resampled |
| Data acquisition (§4.6) | `search_data_sources`/`get_dataset_licence_info`/`check_api_credentials` tested against mocked provider responses (no live network calls in the automated suite). `resolve_place` tested against cached real responses committed as fixtures, including a deliberately ambiguous name (Sudbury) asserting that REQ-9 returns the candidate list rather than a single pick, and an unambiguous one asserting it proceeds without one; `download_and_register_layer` covered by a single opt-in integration test against a known small real dataset, run manually/occasionally rather than in the default automated pass, since it depends on external services being up and credentials being present. Provider adapters (§3.1) are tested individually against recorded real responses committed as fixtures — one recorded response per provider is enough to pin its parsing, and adapters being separable is precisely what makes this tractable rather than needing a five-provider mock. Dispatcher-level tests cover REQ-10 directly: inject one failing, one timing-out and one credential-less adapter, assert the menu still returns the successful providers' results with per-provider statuses attached |
| Processing algorithms | Output feature/pixel count, geometry validity (`isGeosValid()`), attribute value spot-checks against hand-calculated expected results on the synthetic fixture |
| Terrain/export tools (§4.7) | Output file exists, correct format/dimensions, raster statistics within expected range (e.g. heightmap min/max matches source DEM min/max after normalisation), georeferencing bounds match input extent. For `export_heightmap` specifically, assert the REQ-11 contract: bit depth is ≥16, the returned elevation range matches the fixture DEM's true min/max, and a fixture containing nodata cells normalises from the real range rather than from the nodata sentinel — the last of these is the failure that looks fine until it is rendered |
| `model_sea_level_change` | Known synthetic DEM + known threshold → deterministic, hand-computable land/water polygon count and area. Assert explicitly that the source DEM's statistics are **unchanged** after the call, since the whole point of the thresholding approach is that the DEM is not mutated. Fixture includes a landlocked below-threshold basin so the `connectivity` option is covered both ways: bathtub floods it, ocean-connected does not |
| Screenshot/render tools | File exists, correct dimensions/format, non-blank (basic pixel-variance check) as an automated floor; Claude can additionally open and visually sanity-check the image directly when running the test session, as a secondary check beyond the automated assertion |
### 9.4 Live-mode smoke tests
For the TCP-listener plugin (§2, interactive mode), full unit coverage isn't practical to automate unattended. Instead: a small smoke-test script that launches QGIS with the plugin loaded, opens the fixture project, runs 3–4 representative calls over the socket (one from each tool category), and asserts the responses — enough to catch "the listener is broken" without needing GUI interaction. This runs less frequently than the headless suite (e.g. before a release/merge point) rather than on every change.
### 9.5 Requirements (EARS)
**REQ-T1:** WHEN a new tool is implemented, THEN a corresponding automated test using the synthetic fixture data SHALL be added in the same task/commit, per the SDD tasks.md breakdown — no tool is considered "done" without its test.
**REQ-T2:** WHEN the test suite is run, THEN it SHALL execute entirely via the headless path and require no manual QGIS GUI interaction, so Claude Code can run and interpret it unattended.
**REQ-T3:** WHEN a test fails, THEN the failure output SHALL include the expected vs actual structured values (not just pass/fail), so the agent can diagnose and fix without needing Chloe to reproduce the issue manually.
**REQ-T4:** WHERE a tool's correctness genuinely cannot be reduced to a structured assertion (e.g. cartographic "does this look good" styling questions), THEN the test SHALL still assert the mechanical basics (file produced, correct dimensions, non-blank), and the remaining visual judgement SHALL be explicitly flagged in the task as needing a one-off human check rather than silently assumed to be covered.
### 9.6 Practical effect on the build order
Testing isn't a separate late-stage phase — it's folded into each step in §7: every tool task includes writing its fixture-based test as part of the same unit of work, so the suite grows alongside the tool surface rather than being retrofitted. The synthetic `test-data/` fixtures are created once, early, as task 0 in §7, since almost everything downstream depends on them.
